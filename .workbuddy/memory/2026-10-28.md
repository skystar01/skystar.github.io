## 新增第 11 款游戏：概率扫雷（game-mine）

在游戏中心新增「概率扫雷」，核心差异化是把 AI 的不确定性可视化（爆炸概率热力图），
而非常规的「高亮安全格」。

### 接入路径（新增游戏要改 6 处，容易漏）

1. `index.html` — `.game-tab[data-game="mine"]`（含 SVG 图标）+ `.game-container.game-mine`
2. `styles/game-mine.css` — 复用 `--game-*` 主题变量
3. `src/game-mine.js` — 渲染与交互层
4. `src/mine-solver.js` — 棋盘 + 概率求解器（纯逻辑，可 Node 校验）
5. `src/app.js` — `ensureMineScript()` 懒加载分支 + `fitGame` 的 `case 'mine'`
6. `src/game-feedback.js` — **最容易漏**：统一状态栏/结算浮层的 games 映射表
7. `README.md` — 顺带修正了早已过时的「8 个游戏」表格（实际 11 个，来源列还写着 app.js）

### 架构决策

- 扫雷走**独立懒加载**（同 game-plane.js），不塞进已 8726 行的 games-bundle.js。
- 求解器单独成 `mine-solver.js`：因为需要脱离 DOM 做统计校验，与渲染耦合就无法测试。
- 结算浮层**复用 game-feedback** 的统一机制，不自建。最初写了 `.mine-overlay`，
  结果与统一浮层叠加成两层，已删除。

### 踩到的坑

1. `studio.css` 把「游戏目录 / 10」写死在 `::before` 的 content 里，加第 11 个游戏后不更新。
   已改为 JS 注入 `--game-count` CSS 变量，CSS 用 `content: '游戏目录 / ' var(--game-count)`，
   日后加游戏自动同步。
2. `game-center.css` 有 `.game-container{display:none !important}`，`!important` 压过
   高特异性选择器。游戏容器里**不能写 display**，否则容器永不显示，显隐必须交给 `.active`。
3. 切难度/重开局时清空了 `prob` 但没重算，导致提示开着却热力图整片消失。已补 `#refreshProb()`。
4. game-feedback 的「暂停/继续」是同一个按钮，需要 toggle 语义；而 tab 切换用的是幂等的
   pause/resume。两者不能混用，已单独加 `togglePause()`。

### 求解器：一个真实的算法 bug

初版把「边界格雷数 === 剩余雷数」当硬约束（相当于假定边界之外一颗雷都不放），
统计校验抓出 easy 档 22 例「判定必然安全却踩雷」的误判。

修正：边界之外的自由格以组合数 `C(N, t)` 权重参与卷积，DP 变成
`T = Σ_m F(m) · C(N, R−m)`。修完三档误判全部归零。

教训对应上了既有铁律：**构建通过只是形式检查**，概率对错必须单独做统计自检。

### 验证方式（可复用）

- `node tools/verify-mine-solver.mjs`：确定性结论零误判、概率校准分桶、Brier 分数、求解耗时。
  目前 easy/medium/hard 的 Brier 分别约 0.038 / 0.176 / 0.175（0.25 ≈ 盲猜），
  高级盘面求解平均 0.34ms、最慢 3.37ms，远低于 AI 自动模式的 260ms 步进预算。
- 浏览器端用 Playwright 做了冒烟（首点连锁展开、热力图分层、AI 自动推进、三档格子数、
  切难度状态保留），验证完已删除脚本。

### 已知局限

50% 以上的高概率尾部轻微高估（60-69% 桶实际约低 3-4%）。样本 300+ 时接近噪声量级，
且不影响实际用途（AI 选的是概率最低格）。若要收紧需处理 interior 均摊近似的误差。

## 性能排查：「飞机大战加载 20 秒」的真实原因

用户怀疑是代码体积 / 懒加载失效。实测否决：飞机 chunk 只有 62.6KB(16KB gzip)。

真因在 `games-bundle.js` 末尾两个 `whenDomReady`：包一加载就构造了
`new MemoryGame()`(预载 8 张卡面 690KB) 和 `new SurvivorGame()`(预载 7 张精灵 1.6MB,
其中 player-clean.png 单张 1.2MB)。所有游戏容器都写死在 index.html 里,
所以「切进游戏中心」瞬间 2.3MB 同时发出, 把带宽打满; 飞机 chunk 排后面干等。

线上 A/B（拦截这批图）: 8899ms → 904ms, 快 9.8 倍 —— 因果成立。

### 修复与结果（线上实测）

| 指标 | 修前 | 修后 |
|---|---|---|
| 进游戏中心传输 | 2602KB | 275KB |
| 飞机就绪 | 8899ms | 936ms |
| 霜境星火精灵就绪 | ~10s | 1526ms |
| 记忆翻牌卡面就绪 | — | 583ms |

改动：
1. 暴露 `ensureMemoryGame` / `ensureSurvivorGame`，在 `fitGame` 对应分支按需构造。
   **survivor 的 ensure 必须在 fitSurvivor 之前**，否则 canvas 是默认尺寸。
2. 图片超配压缩：player-clean 1254²→400² WebP（1212KB→41KB），
   卡面 2048²→320²（738KB→65KB）。工具用 Chromium canvas 重采样，
   环境里没有 ImageMagick（`/c/Windows/System32/convert` 是 FAT 转换工具，别误用）。
   压缩后必须验透明通道：读角点 alpha，确认 = 0。

### 方法论

和我之前的铁律一致：**先量再改**。这次差点顺着「代码太长所以慢」的直觉去拆包，
但拆包对 20 秒几乎无效（chunk 本来就只有 16KB）。用 A/B 对照（拦截资源）
把因果钉死，比读代码猜快得多。

### 仍未处理（按收益排序）

- **Font Awesome + Google Fonts 是现在更大的负担**：cdnjs 的 all.min.css 实测
  4.4s(本地)/9.5s(fa-brands woff2, 线上)，fa-solid-900.woff2 124KB、fa-brands 102KB、
  Google Fonts css2 121KB。而全站只用了 9 个 `<i class="fa-...">`。
  改内联 SVG 可省 226KB 字体 + 15KB CSS + 2 次跨域往返。
- **games-bundle 8726 行可按游戏拆分**：进游戏中心目前加载整个 47KB(gzip) 包，
  拆分后每个游戏约 5-12KB。收益主要在可维护性与独立缓存，不在首屏速度。

### 修掉 P1 的一个真 bug

P1 里预设按钮标签被我写死成 `['弱','标准','强']`，但扫雷的 preset 键是「慢/标准/快」、

### 验证「权重真的影响决策」时差点误判

第一版测试：固定地形 + T 型，三组权重给出**同一个落点**。第一反应是「权重没生效」，
但查证发现评估分数确实不同（-15.2 / -34.8 / 0），只是该地形存在压倒性最优解。
扫了 400 个随机地形才找到能翻转的固定用例：
- T 型 on heights [3,7,1,1,0,0,0,7,0,5]: 标准 x4 / 平整优先 x8（旋转也不同）
- L 型 on heights [1,1,0,6,5,2,5,8,7,2]: 标准 x0 / 平整优先 x4

**方法论**：一次「结果相同」不能直接推出「机制没生效」，得先量中间量（评分）。
反过来也成立 —— 「分数不同」不能直接推出「决策会不同」。

### 精度取舍

滑杆 step 0.01，默认值取经典系数的两位近似（-0.51 等）。实测 20 个随机局面下
两位近似与原始六位精度（-0.510066）决策 **20/20 一致**，注释里已按实测范围写清，
不写「完全一致」这种无法证伪的话。

## 井字棋：搜索与规则不一致 + ε-greedy 难度档（feat 6d0e16b / 737c9a1）

### 规则先说清

这款井字棋不是标准棋：**每方最多 3 子，落下第 4 子时最早的消失**。
因此棋盘永远填不满 → `checkDraw` 几乎不会触发 → 这个变体没有平局，只能靠连成三子分胜负。

### 挖出的 bug

原 `minimax` 搜的是静态棋盘，**完全没建模"棋子会消失"**——搜索里走的规则和实际规则不一致。
实测随机乱走的玩家 200 局赢 14 局（7%），所谓"不可战胜"是假的。

修复：把双方出子队列纳入搜索状态（落子→入队→超过 3 个移除最早的），配 alpha-beta、
深度上限与「两子一空」威胁估值。回滚顺序必须与落子相反（`_unplace`：先恢复被挤掉的老子、
再弹出新子、最后清空落点）。

### 两次过度承诺，都被数据否掉

1. **「0% 不可战胜」不成立**：200 局样本是 100%，但 500 局样本仍输 1–3 局。
   而且**加深搜索没有改善**：深度 5 输 1 局、深度 6 输 3 局、耗时翻倍。
   → 瓶颈在深度上限处的静态估值（看不到消失后果），不是搜得不够深。
2. **「10% 档还原旧手感」不成立**：那是旧 ε 实现下的数字，换标准 ε 后不成立，已从 README 删除。

### ε-greedy 的实现错误

第一版写成「随机换一个**非最优**位置」，这不是 ε-greedy：ε=100% 也只是在次优里打转，
胜率只降到 62%。标准做法是「从**全部合法位置**随机选」，这样 ε=100% 才是纯随机（胜率 76–89%）。

### 标定（对随机对手，各 200 局）

| 失误率 | 0% | 10% | 35% | 50% |
|---|---|---|---|---|
| AI 胜率 | 100% | 94–98% | 89% | 76% |

**注意**：这只是对随机对手的代理指标，真人体验需要自己调；不能当"对玩家胜率"用。

### 规则层面的不平衡（未改，待拍板）

双方都纯随机 500 局：**后手胜 367 局（73%）**。因为先落子的一方更早开始丢子，
先手在该变体里是劣势。AI 固定执后手 → 天然占优。也就是说玩家"总赢不了"有相当一部分
来自规则，不只是 AI 强。要平衡可考虑：先手多留一子 / 可选先后手 / AI 轮流先后手。

- 井字棋默认是**双人模式**，参数要先点「AI 模式」才生效，提示里已注明。
- 跑分台新增胜率指标：赢记 100 / 输记 0，均值即胜率；`defaultRuns=30`（胜率步长 1/N）。
- 跑分时临时屏蔽 `updateScore` / `highlightWin`，避免污染战绩与 DOM。

## 井字棋开局随机先后手（feat f22e1b1）

用户确认「3 子上限」是有意为难度设计的，不动规则；先后手改为开局随机。

实现：
- `init()` 里 `Math.random() < 0.5` 决定先后手；AI 模式按人/AI 分，双人模式按 X/O 分；
- AI 抽到先手时自己 600ms 后落子，不用等玩家点第一格；
- **`initToken` 防抖**：连续点重开会叠加多个定时器，旧定时器会替新局白走一步。
  这类"回调属于上一局"的问题在 RAF/定时器驱动的游戏里很常见，值得记住这个手法。

连带修正：
- **跑分驱动必须按 `currentPlayer` 归属执行**。原来的循环固定「玩家一手、AI 一手」，
  而 `makeMove()` 根本不校验回合归属 —— AI 先手的局会被驱动"替 AI 落子"，跑出来的数据是错的。
- 重新标定（随机先后手，各 200 局，对手随机）：0% 100%、10% 98%、35% 88%、50% 81%。
  与随机前基本一致，说明先后手随机没有削弱强档。

实测：本地 196/400、线上 200/400 由 AI 先手。

### 教训

改了「谁先走」这种看似局部的规则，**所有假设固定先后手的下游代码都要重新审视** ——
这次就抓到了跑分台驱动这一处。凡是"驱动游戏"的代码（跑分、测试、自动化），
都应该按游戏自己的状态走，而不是按预先写死的剧本走。

## 用黑白棋替换记忆翻牌（feat cf9cb71）

用户觉得记忆翻牌「平平无奇」，授权改版或换游戏；确认换成黑白棋。

### 为什么换

记忆翻牌只有「记性」一个维度：调到 100% 碾压玩家、30% 变随机乱翻，**滑杆没有中间地带**，
不适合当调参面板的载体。黑白棋评估是四项加权和（角/边/行动力/子数），
角权重调 0 会主动送角 —— 参数到行为的因果肉眼可见。

### 实现要点

- 独立懒加载 `src/game-reversi.js`（8.1KB / 3.3KB gzip），不进 8.7k 行的公共包；
- negamax + α-β，候选按角→边→内部排序；深度 1–5；
- 评估：`w角·角差 + w边·边差 + w行动力·可落点数差 + w子数·子数差`；
- 无处可落自动轮空；双方都无子可落才结束（这个变体**没有平局**，按子数定胜负）；
- 实验台 5 参数、预设 贪吃/标准/稳健、底部实时评估式；
- 跑分按「终局子数差」（AI 执黑 vs 随机执白）：贪吃 21 vs 标准 38；
- 遥测：候选落点数 / 评估分 / 深度。

### 三个坑（都值得记）

1. **手写候选顺序表**（`SCAN_ORDER`）有重复项且漏格。漏格会让合法落点被跳过 ——
   这是规则级错误，测试用「开局必须是 4 个合法点」才抓到。改为代码生成，别手写索引表。
2. **说明文字被浮层压住**：第一反应是加 `padding-bottom`，量了盒模型才发现根因是
   **内容总高刚好顶满容器**（不会溢出到 padding 里）。最终把说明移到棋盘上方 + fit 多留 28px。
3. **又犯了「先写数字后测」**：深度耗时提示初稿写「深度 4 约 120ms」，实测 16ms。
   这个毛病在这个项目里已经出现三次（2048 深度、井字棋搜索、黑白棋深度），
   以后凡是 UI 里出现性能数字，先跑采样再写。

### 实测数据

中后盘（最多 15 个合法落点）单步耗时：深度 3 约 3ms、深度 4 约 16ms、深度 5 约 55ms（最慢 130ms）。

## 游戏接入收口（refactor 8fdf13b）

把「新增游戏要改 9 处、漏了不报错」压到「4 处 + 一条自检」。

### 改了什么

1. **GAME_META 一张表**（app.js）：`{ load, fit }`。原来是 setActiveByGame 的 4 分支
   if/else + fitGame 的 11 个 case，加游戏要改两处。
2. **图标基类 `.game-icon`**：原来四组选择器按类名逐个列举，漏加 = 没有宽高 = 看不见。
   现在挂基类就有尺寸，专属 `.icon-xxx` 只留作额外动效。
   坑：`.game-tab [class^="icon-"]` 在类名前加 `game-icon` 后会失配，必须补 `.game-icon` 选择器。
3. **启动自检 `__gameAudit()`**：逐 tab 检查「状态读数 / 容器 / GAME_META / .game-icon」，
   控制台以 `[游戏清单自检]` 点名。暴露到 window 便于复核。

### 方法论

这类「漏了不报错」的同步点，靠纪律记住是不可靠的（我这次就是漏了图标）。
**要么消除同步点（清单/基类），要么加机器检查（自检）**，两者至少要有一个。

自检本身也要验证有效：人为删掉一个 `.game-icon`、删掉一个 `GAME_META` 项，
确认它确实点名——一个从不报警的检查可能根本是坏的。
