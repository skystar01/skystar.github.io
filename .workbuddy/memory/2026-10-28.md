## 新增第 11 款游戏：概率扫雷（game-mine）

在游戏中心新增「概率扫雷」，核心差异化是把 AI 的不确定性可视化（爆炸概率热力图），
而非常规的「高亮安全格」。

### 接入路径（新增游戏要改 6 处，容易漏）

1. `index.html` — `.game-tab[data-game="mine"]`（含 SVG 图标）+ `.game-container.game-mine`
2. `styles/game-mine.css` — 复用 `--game-*` 主题变量
3. `src/game-mine.js` — 渲染与交互层
4. `src/mine-solver.js` — 棋盘 + 概率求解器（纯逻辑，可 Node 校验）
5. `src/app.js` — `ensureMineScript()` 懒加载分支 + `fitGame` 的 `case 'mine'`
6. `src/game-feedback.js` — **最容易漏**：统一状态栏/结算浮层的 games 映射表
7. `README.md` — 顺带修正了早已过时的「8 个游戏」表格（实际 11 个，来源列还写着 app.js）

### 架构决策

- 扫雷走**独立懒加载**（同 game-plane.js），不塞进已 8726 行的 games-bundle.js。
- 求解器单独成 `mine-solver.js`：因为需要脱离 DOM 做统计校验，与渲染耦合就无法测试。
- 结算浮层**复用 game-feedback** 的统一机制，不自建。最初写了 `.mine-overlay`，
  结果与统一浮层叠加成两层，已删除。

### 踩到的坑

1. `studio.css` 把「游戏目录 / 10」写死在 `::before` 的 content 里，加第 11 个游戏后不更新。
   已改为 JS 注入 `--game-count` CSS 变量，CSS 用 `content: '游戏目录 / ' var(--game-count)`，
   日后加游戏自动同步。
2. `game-center.css` 有 `.game-container{display:none !important}`，`!important` 压过
   高特异性选择器。游戏容器里**不能写 display**，否则容器永不显示，显隐必须交给 `.active`。
3. 切难度/重开局时清空了 `prob` 但没重算，导致提示开着却热力图整片消失。已补 `#refreshProb()`。
4. game-feedback 的「暂停/继续」是同一个按钮，需要 toggle 语义；而 tab 切换用的是幂等的
   pause/resume。两者不能混用，已单独加 `togglePause()`。

### 求解器：一个真实的算法 bug

初版把「边界格雷数 === 剩余雷数」当硬约束（相当于假定边界之外一颗雷都不放），
统计校验抓出 easy 档 22 例「判定必然安全却踩雷」的误判。

修正：边界之外的自由格以组合数 `C(N, t)` 权重参与卷积，DP 变成
`T = Σ_m F(m) · C(N, R−m)`。修完三档误判全部归零。

教训对应上了既有铁律：**构建通过只是形式检查**，概率对错必须单独做统计自检。

### 验证方式（可复用）

- `node tools/verify-mine-solver.mjs`：确定性结论零误判、概率校准分桶、Brier 分数、求解耗时。
  目前 easy/medium/hard 的 Brier 分别约 0.038 / 0.176 / 0.175（0.25 ≈ 盲猜），
  高级盘面求解平均 0.34ms、最慢 3.37ms，远低于 AI 自动模式的 260ms 步进预算。
- 浏览器端用 Playwright 做了冒烟（首点连锁展开、热力图分层、AI 自动推进、三档格子数、
  切难度状态保留），验证完已删除脚本。

### 已知局限

50% 以上的高概率尾部轻微高估（60-69% 桶实际约低 3-4%）。样本 300+ 时接近噪声量级，
且不影响实际用途（AI 选的是概率最低格）。若要收紧需处理 interior 均摊近似的误差。

## 扫雷专属图标设计（本轮）

替换掉原来的「网格 + 八角星」（与概率无关、辨识度低）和标题区 emoji 💣。

选型过程：试了「雷 + 概率弧环 / 雷达楔形 / 3×3 热力格 / 环状进度雷」四组，
**八尖角 + 圆体在任何组合下都会读成太阳或病毒**；旗子的轮廓独一无二、
20px 下不糊，最终定为旗子。

定稿：旗杆 + 底座 + 旗面四段递减不透明度（模拟概率渐变）。

**坑**：侧边栏 tab 会被 JS `cloneNode` 复制成无限轮播副本，
所以图标里**不能用 `linearGradient` + `url(#id)`** —— id 会重复。
改用分段 path + `opacity` 模拟渐变，无 id 依赖，克隆安全。

尺寸规则必须写进 `main.css`（全局），不能写 `game-mine.css`：
后者随游戏 chunk 懒加载，tab 图标在那之前就已渲染，会短暂无样式。

## 性能排查：「飞机大战加载 20 秒」的真实原因

用户怀疑是代码体积 / 懒加载失效。实测否决：飞机 chunk 只有 62.6KB(16KB gzip)。

真因在 `games-bundle.js` 末尾两个 `whenDomReady`：包一加载就构造了
`new MemoryGame()`(预载 8 张卡面 690KB) 和 `new SurvivorGame()`(预载 7 张精灵 1.6MB,
其中 player-clean.png 单张 1.2MB)。所有游戏容器都写死在 index.html 里,
所以「切进游戏中心」瞬间 2.3MB 同时发出, 把带宽打满; 飞机 chunk 排后面干等。

线上 A/B（拦截这批图）: 8899ms → 904ms, 快 9.8 倍 —— 因果成立。

### 修复与结果（线上实测）

| 指标 | 修前 | 修后 |
|---|---|---|
| 进游戏中心传输 | 2602KB | 275KB |
| 飞机就绪 | 8899ms | 936ms |
| 霜境星火精灵就绪 | ~10s | 1526ms |
| 记忆翻牌卡面就绪 | — | 583ms |

改动：
1. 暴露 `ensureMemoryGame` / `ensureSurvivorGame`，在 `fitGame` 对应分支按需构造。
   **survivor 的 ensure 必须在 fitSurvivor 之前**，否则 canvas 是默认尺寸。
2. 图片超配压缩：player-clean 1254²→400² WebP（1212KB→41KB），
   卡面 2048²→320²（738KB→65KB）。工具用 Chromium canvas 重采样，
   环境里没有 ImageMagick（`/c/Windows/System32/convert` 是 FAT 转换工具，别误用）。
   压缩后必须验透明通道：读角点 alpha，确认 = 0。

### 方法论

和我之前的铁律一致：**先量再改**。这次差点顺着「代码太长所以慢」的直觉去拆包，
但拆包对 20 秒几乎无效（chunk 本来就只有 16KB）。用 A/B 对照（拦截资源）
把因果钉死，比读代码猜快得多。

### 仍未处理（按收益排序）

- **Font Awesome + Google Fonts 是现在更大的负担**：cdnjs 的 all.min.css 实测
  4.4s(本地)/9.5s(fa-brands woff2, 线上)，fa-solid-900.woff2 124KB、fa-brands 102KB、
  Google Fonts css2 121KB。而全站只用了 9 个 `<i class="fa-...">`。
  改内联 SVG 可省 226KB 字体 + 15KB CSS + 2 次跨域往返。
- **games-bundle 8726 行可按游戏拆分**：进游戏中心目前加载整个 47KB(gzip) 包，
  拆分后每个游戏约 5-12KB。收益主要在可维护性与独立缓存，不在首屏速度。

## AI 实验台 P2（feat d06e260）

### 修掉 P1 的一个真 bug

P1 里预设按钮标签被我写死成 `['弱','标准','强']`，但扫雷的 preset 键是「慢/标准/快」、
迷宫是「温和/标准/凶狠」——**这两款各有一半档位点不到，点了「弱」还会写进一个
不存在的预设名**。改为从 `Object.keys(entry.presets)` 渲染。
教训：schema 驱动就得彻底，任何写死的枚举都是下一个 bug。

### 验证「权重真的影响决策」时差点误判

第一版测试：固定地形 + T 型，三组权重给出**同一个落点**。第一反应是「权重没生效」，
但查证发现评估分数确实不同（-15.2 / -34.8 / 0），只是该地形存在压倒性最优解。
扫了 400 个随机地形才找到能翻转的固定用例：
- T 型 on heights [3,7,1,1,0,0,0,7,0,5]: 标准 x4 / 平整优先 x8（旋转也不同）
- L 型 on heights [1,1,0,6,5,2,5,8,7,2]: 标准 x0 / 平整优先 x4

**方法论**：一次「结果相同」不能直接推出「机制没生效」，得先量中间量（评分）。
反过来也成立 —— 「分数不同」不能直接推出「决策会不同」。

### 精度取舍

滑杆 step 0.01，默认值取经典系数的两位近似（-0.51 等）。实测 20 个随机局面下
两位近似与原始六位精度（-0.510066）决策 **20/20 一致**，注释里已按实测范围写清，
不写「完全一致」这种无法证伪的话。
